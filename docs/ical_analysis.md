# Анализ RFC 5545 (iCalendar) и компонента VEVENT

Документ RFC 5545 описывает формат данных iCalendar, который используется для обмена календарной информацией (событиями, задачами, свободным/занятым временем). В контексте задач парсинга и сбора календарей, `VEVENT` — наиболее часто используемый компонент.

Актуальный уровень поддержки RFC 5545 в библиотеке описан в `README.md`.

## Что обязательно поддерживать в VEVENT (Mandatory)

Для того чтобы событие считалось валидным по стандарту, парсер и генератор **обязаны** обрабатывать следующие свойства:

- **`UID`**: Уникальный глобальный идентификатор события. Критически важен для дедупликации и обновления событий.
- **`DTSTAMP`**: Дата и время создания/модификации самого объекта iCalendar (не путать с временем начала события). Используется для разрешения конфликтов при синхронизации (какая версия новее).
- **`DTSTART`**: Дата и время начала события. Обязателен (если только компонент не используется внутри метода `METHOD`, где действуют свои правила, но в 99% случаев он есть).

## Что желательно поддерживать (Optional, but highly recommended)

Без этих свойств календарь теряет большую часть своей полезности для конечного пользователя:

- **`DTEND` / `DURATION`**: Конец события или его длительность. По стандарту может присутствовать только что-то одно. Если нет ни того, ни другого, событие считается однодневным (если DTSTART типа DATE) или не имеющим длительности (DATE-TIME).
- **`SUMMARY`**: Краткое название (заголовок) события.
- **`DESCRIPTION`**: Подробное описание события.
- **`LOCATION`**: Место проведения.
- **`RRULE`, `RDATE`, `EXDATE`**: Правила повторения событий (Recurrence Rules), даты повторений и исключения из правил. Сложнейшая часть парсинга, но без неё не работают регулярные встречи (например, "каждый понедельник").
- **`STATUS`**: Статус (TENTATIVE, CONFIRMED, CANCELLED). Важно для отмененных событий.
- **`TRANSP`**: Прозрачность времени (OPAQUE - занят, TRANSPARENT - свободен). Влияет на отображение занятости (Free/Busy).
- **`ORGANIZER` / `ATTENDEE`**: Организатор и участники.
- **`SEQUENCE`**: Порядковый номер ревизии события. Если событие обновлено (например, изменено время), `SEQUENCE` увеличивается. Помогает понять, нужно ли обновлять локальную копию.

## Важные моменты для реализации парсера iCal

Реализация парсера iCalendar содержит множество подводных камней, которые строго описаны в RFC 5545:

1. **Разделители строк (Line Breaks)**
   - По стандарту строки заканчиваются последовательностью `CRLF` (`\r\n`). 
   - На практике многие системы генерируют файлы только с `LF` (`\n`). Парсер должен быть устойчив к обоим вариантам.

2. **Сворачивание строк (Line Folding)**
   - Ограничение длины строки составляет 75 октетов (байт). 
   - Если строка длиннее, она переносится на следующую строку, при этом следующая строка должна начинаться с символа пробела (SPACE) или табуляции (HTAB).
   - **Важно:** Перед парсингом файла необходимо выполнить разворачивание строк (Unfolding) — удалить последовательность `CRLF` и следующий за ней пробел/табуляцию.

3. **Кодировка**
   - По умолчанию и единственно правильно — **UTF-8**.

4. **Экранирование символов (Escaping)**
   - В текстовых значениях символы переноса строки кодируются как `\n` или `\N`.
   - Запятые и точки с запятой экранируются обратным слешем: `\,` и `\;`.
   - Обратный слеш: `\\`.

5. **Даты, время и часовые пояса (Timezones)**
   - Даты могут быть в формате локального времени с указанием часового пояса в параметре (مثلا: `DTSTART;TZID=Europe/Moscow:20231024T120000`).
   - Время по Гринвичу (UTC) обозначается суффиксом `Z` (`DTSTART:20231024T090000Z`).
   - Формат типа 'ДАТА' (только день) без времени (`DTSTART;VALUE=DATE:20231024`).
   - Парсер должен уметь распознавать эти три формы и корректно приводить их к нужной временной зоне, используя системную БД часовых поясов или компонент `VTIMEZONE` из самого файла.

6. **Структура Строки**
   - Строка состоит из: `ИмяСвойства[;Параметр1=Значение1;Параметр2=Значение2]:ЗначениеСвойства`.
   - Пример: `ATTENDEE;ROLE=REQ-PARTICIPANT;PARTSTAT=ACCEPTED:mailto:user@example.com`

Учитывая эти особенности, рекомендуется использовать существующие лексеры и парсеры для базового разбора структуры (Unfolding, разделение на параметры и значения), концентрируясь на бизнес-логике обработки полученных компонентов.
